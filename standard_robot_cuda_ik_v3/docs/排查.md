> **Medium SR 不应该低于 Strict SR。**

你给的数据里：

5. success rate 统计对象不同；

# 三、最重要的技术判断

## 1. “GPU 并行化潜力巨大”这个判断是对的，但不能写成 overhead 为零

你说：

> 多 seed 在 Python 中 16× 慢于单 seed，但在 GPU 上 Grid(N,K) 可将 K 个 seed 完全并行化，预期 overhead 接近零。

这个方向对，但“overhead 接近零”不能这么绝对写。

更严谨地说：

> 在 GPU 上，multi-seed 可通过 `Grid(N,K)` 将不同 seed 映射为独立 block。当 `N×K` 未超过 GPU 并行吞吐饱和区间时，增加 seed 数主要提升并行占用率，额外墙钟时间可能远小于 CPU 串行的 K 倍；当 `N×K` 超过硬件并行容量后，时间仍将随总工作量增长。

也就是说：

* 小 N：multi-seed 可能几乎“免费”，因为 GPU 本来没吃满；
* 大 N：multi-seed 不可能完全免费，因为总 block 数变成 `N×K`；
* 但是它仍然可能比 Python/CPU 串行快一个数量级。

这个表述更科学。

---

## 2. Multi8 的 pos_p95=6.35mm 与 Strict SR=93.5% 并不矛盾

Strict 阈值是 5mm。如果 SR=93.5%，说明还有 6.5% 的失败样本。

p95 是第 95 百分位，已经落入失败样本区间，所以 p95=6.35mm 是合理的。

但论文里要明确区分：

| 指标                      | 含义              |
| ----------------------- | --------------- |
| all-target pos_p95      | 包含失败样本，反映长尾     |
| successful-only pos_p95 | 只统计成功样本，反映成功解质量 |

建议后续表格同时给两列。否则读者会疑惑：既然 Strict 阈值 5mm，为什么 p95 是 6.35mm。
