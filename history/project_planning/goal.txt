# 任务总目标

在 `/mnt/linuxdata/cuda_ik_accelerateion/` 目录下新建一个独立子项目文件夹，用于完成一套新的标准化 CUDA 批量逆运动学性能研究工作。

新工作的论文核心不再是“自定义 UR10+铲斗装配体狭窄空间轨迹求解”，而是：

**面向标准机械臂批量逆运动学求解的 CUDA 底层优化框架与性能分析。**

核心研究问题是：

**在消费级 NVIDIA RTX 4060 Laptop GPU 上，如何通过 CUDA 底层线程映射、寄存器级小矩阵求解、共享内存布局、常量内存广播、Kernel Fusion、批量任务组织等硬件适配手段，实现机器人批量逆运动学求解的极致性能。**

注意：

本项目不是为了包装“新 IK 算法”，也不是为了证明某个 LM/DLS 参数更优，而是要证明：

**针对机器人 IK 这种小规模、高频、大批量任务，通过 CUDA 底层结构适配，可以比通用求解框架获得更高的单位硬件效率。**

本项目只研究：

1. 批量逆运动学求解；
2. CUDA 底层性能优化；
3. 标准机械臂模型上的可复现实验；
4. 消融实验；
5. Nsight Compute / Roofline 性能分析；
6. 7DOF 扩展适配分析。

本项目不研究：

1. 全局路径规划；
2. 避障路径规划；
3. 轨迹优化；
4. 完整运动规划流水线；
5. MoveIt 规划器性能比较；
6. 碰撞检测系统。

不要把随机目标点测试写成“路径规划”或“运动规划”，应统一称为：

**随机可达目标位姿集上的批量逆运动学求解性能测试。**

# 二、主实验改为官方 UR10 模型

## 目标

将主实验对象改为官方标准 UR10 机械臂模型，而不是当前自定义 UR10+铲斗装配体。

要求：

1. 使用标准 UR10 URDF；
2. 不再使用铲斗 TCP；
3. 不再使用 wrist_2 负 Z 轴等自定义装配体特性；
4. 统一所有求解器的机器人模型、TCP、关节限位、目标位姿定义；
5. 所有求解器必须使用同一批目标位姿数据；
6. 所有结果必须明确记录模型来源、URDF路径、MD5值、关节链、TCP定义。

## 必须完成的验证

请编写脚本验证：

1. UR10 关节数量是否为 6；
2. 各关节轴方向；
3. 各关节原点；
4. TCP 坐标系；
5. FK 结果是否与 CPU Eigen/KDL 参考实现一致；
6. CUDA FK 与 CPU FK 的最大误差；
7. cuRobo、PyRoki、KDL 等求解器是否使用了完全一致的 URDF 和 TCP。

## 求解器模型一致性处理规则

cuRobo、PyRoki、KDL、TRAC-IK 等求解器可能对 URDF、TCP、joint limits 或 base frame 的解析方式不同。

必须执行以下规则：

5. 不能在模型不一致的情况下声称性能比较完全公平。

输出验证报告：

`/mnt/linuxdata/cuda_ik_accelerateion/docs/logs/official_ur10_model_verification.md`

报告必须包含：

1. URDF 路径；

# 三、随机生成可达目标位姿集

## 目标

建立标准化、可复现的目标位姿生成流程。

不是随便在空间中生成点，而是：

**随机生成可达目标位姿集，并进行批量 IK 求解性能测试。**

## 生成原则

1. 固定随机种子，例如 `seed=42`；
2. 先随机采样关节角 q；
3. 使用标准 UR10 FK 生成目标位姿 T；
4. 这样保证目标位姿必然可达；
5. 所有求解器使用完全相同的目标位姿集；
6. 保存目标位姿、原始关节角、目标编号；
7. 所有目标数据保存为 CSV 和 JSON 两种格式；
8. Markdown 只作为报告，不作为唯一数据源。

## 目标规模

至少生成以下规模：

```text
N = 100
N = 500
N = 1000
N = 5000
```

如果运行时间可接受，可增加：

```text
N = 10000
```

## 位姿内容

目标数据必须包含：

1. target_id；
2. q_sampled[6]；
3. position x,y,z；
4. rotation matrix 3×3；
5. quaternion；
6. homogeneous transform 4×4；
7. 是否位于关节限位内；
8. 是否通过 FK 复验。

输出目录：

`/mnt/linuxdata/cuda_ik_accelerateion/standard_robot_cuda_ik/data/targets/`

同时输出说明文档：

# 五、主性能对比实验

## 目标

对标准 UR10 批量 IK 求解进行公平 benchmark。

比较对象至少包括：

1. 自研 CUDA 6DOF IK；
2. cuRobo；
3. PyRoki；
4. KDL 或 TRAC-IK；
5. CPU Numeric DLS baseline。

如果 HJCD-IK 适配成本过高，可标记为 optional，但要说明原因。

## 统一收敛判据

所有求解器必须尽可能使用统一收敛判据。

建议默认：

```text
position_error < 0.03 m
orientation_error < 0.5236 rad
max_iter = 固定值
```

如果要使用更严格阈值，例如：

```text
position_error < 0.001 m
orientation_error < 0.01 rad
```

必须确保所有求解器都能公平执行，并在报告中说明。

禁止每个求解器使用自己的默认收敛判据后直接比较。

## 三类时间口径

每个求解器必须尽可能区分以下三类时间：

```text
kernel_time_only
gpu_end_to_end_time
host_api_total_time
```

定义如下：

1. `kernel_time_only`：只统计 CUDA kernel 执行时间；
2. `gpu_end_to_end_time`：包含 H2D/D2H、同步、GPU 侧整体执行；
3. `host_api_total_time`：从 Python/C++ API 调用开始到返回结果。

对于非 CUDA 求解器，例如 KDL，至少记录：

```text
host_api_total_time
```

对于 PyRoki/JAX，必须区分：

1. 是否包含首次 JIT 编译时间；
2. warm-up 后重复运行时间；
3. JIT 缓存是否命中。

对于 cuRobo，必须记录：

1. 是否包含图构建；
2. 是否包含数据搬运；
3. 是否包含内部多种子；
4. 是否包含 warm-up。

## 指标

每个求解器必须统计：

1. total time；
2. kernel_time_only；
3. gpu_end_to_end_time；
4. host_api_total_time；
5. p50 latency；
6. p95 latency；
7. p99 latency；
8. throughput targets/s；
9. convergence rate；
10. position error mean / max；
11. orientation error mean / max；
12. iterations mean / max；
13. failure count；
14. 是否使用 GPU；
15. 是否包含 JIT 编译时间；
16. 是否包含数据拷贝时间；
17. 初始种子策略；
18. 实际目标数量 N；
19. repeat count。

每个 N 至少重复运行：


如果耗时允许，使用：

```text

```

必须输出：

# 七、7DOF 扩展实验与 CUDA 适配

## 目标

加入 7 自由度机械臂作为扩展实验，不作为论文主实验，但必须体现 CUDA 框架的可扩展性。

7DOF 扩展不作为主实验录用依据，不得因 7DOF 未完成而阻塞 UR10 主实验、消融实验、Roofline 分析和论文初稿。

2. 或 Kinova Gen3 7DOF；
3. 如果模型获取困难，先保留接口和文档计划，但不得虚构实验结果。

## 7DOF 与 UR10 的对比重点

必须从两个角度详细分析：

## 角度 A：运动学差异

对比 6DOF UR10 与 7DOF 机械臂：

1. 自由度数量；
2. Jacobian 维度：

   * UR10: 6×6；
   * 7DOF: 6×7；
3. Hessian 维度：

   * UR10: 6×6；
   * 7DOF: 7×7；
4. 是否存在冗余自由度；
5. IK 解是否唯一；
6. 是否需要 null-space；
7. 是否需要二级目标函数；
8. 关节限位处理；
9. 奇异性表现；
10. 收敛率影响；
11. 阻尼伪逆和正规方程在 7DOF 下的差异；
12. 二级目标如何影响公平 benchmark。

## 角度 B：CUDA 底层差异

对比 6DOF 与 7DOF 的 CUDA 实现：

1. PaddedMat6x8 → PaddedMat7x8 或 PaddedMat8x8；
2. 6×6 LDLT → 7×7 LDLT；
3. 寄存器数量变化；
4. Shared memory 增加；
5. 每次迭代 FK 调用次数变化；
6. 数值 Jacobian 中心差分：

   * 6DOF: 12 次 FK；
   * 7DOF: 14 次 FK；
7. Hessian 构造线程数：

   * 6×6 = 36；
   * 7×7 = 49；
8. Warp 分工是否需要调整；
9. Occupancy 是否下降；
10. Register spill 风险；
11. Bank conflict 风险；
12. Kernel launch 结构是否保持一致；
13. 性能下降来源拆解；
14. 是否仍然适合 1 Block / target；
15. 是否需要更改 block size；
16. 是否需要模板化支持 DOF=6/7。

## 7DOF 实验要求
