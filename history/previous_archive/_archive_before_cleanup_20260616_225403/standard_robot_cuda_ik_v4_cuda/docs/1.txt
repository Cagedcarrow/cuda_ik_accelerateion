# Final Push: N=500 超越 cuRobo-Graph 的最后一轮 CUDA 优化与论文 MD 生成

## 0. 总目标

当前最终主实现是：

```text
CUDA-V4-Final-K16-OPT4C
= Analytical Jacobian
+ LM
+ Sobol-K16
+ Limit Barrier
+ Smoothness Rerank
+ target-block seed-parallel mapping
+ fused in-block selection
```

已有关键结果：

```text
N=100: CUDA-V4-OPT4C 吞吐、Strict SR、pos_p95 均优于 cuRobo-Graph
N>=500: cuRobo-Graph 吞吐仍更强
CUDA-V4-OPT4C 在所有 N 的 Strict SR 与 pos_p95 均优于 cuRobo-Graph
```

本轮目标只完成前三步：

```text
1. CUDA Graph 小/中 batch E2E 优化；
2. OPT4C Mixed Precision 扫描；
3. 最终论文图表 + 最新论文 Markdown 生成。
```

核心冲刺目标：

```text
尽最大努力让 N=500 的 CUDA-V4-OPT4C 在 throughput 或 valid throughput 上超过 cuRobo-Graph。
```

如果最终 N=500 仍不能超过，也必须生成完整 gap analysis，说明差距来自哪里，并给出论文中可接受的保守表述。

### 2.3 N=500 胜利判据

定义三个等级。

#### A 级胜利：完全超越

```text

且
N=500 CUDA valid throughput >= cuRobo valid throughput * 1.03
且

```

#### B 级胜利：有效吞吐超越

```text

```

#### C 级胜利：接近 cuRobo

```text
N=500 CUDA raw throughput gap <= 10%
或
valid throughput gap <= 10%
且质量明显更好
```

论文表述：中等 batch 下接近 cuRobo 吞吐，并保持更优解质量。

#### 失败

```text
N=500 throughput gap > 10%
且 valid throughput gap > 10%
```

必须输出 gap analysis，不允许伪造成成功。

# 3. Phase A：CUDA Graph E2E 优化

## 3.1 目标

基于 OPT4C-K16 实现 CUDA Graph capture / replay，重点优化：

```text
N=100
N=500
N=1000
```

核心看：

```text
E2E latency
CPU overhead
GPU stream time
repeat stability
N=500 throughput
```

## 3.2 实现要求

新增 runner 参数：

```bash
--graph-mode off
--graph-mode capture_replay
--graph-mode persistent_replay
```

如果已有 graph 支持，则复用；否则新增最小实现。

### graph-mode off

普通 launch，作为对照。

### graph-mode capture_replay

流程：

```text
1. warmup 普通执行；
2. capture 固定 N/K 的完整工作流；
3. instantiate graph；
4. repeat 中只做 graphLaunch；
5. 输出平均值、p50、p95、min、max。
```

### graph-mode persistent_replay

如果数据指针和 buffer 可复用：

```text
1. 初始化时创建固定 N 的 graph；
2. 每轮只更新 input buffer；
3. graphLaunch；
4. 不重复 capture。
```

若实现困难，可只完成 capture_replay。

## 3.3 必须覆盖的 kernel/workflow

至少包含：

```text
OPT4C IK kernel
必要的 memcpy / memset
结果 selection 如果已 fused，则不需要额外 selection kernel
必要的 result copy
```

要分别计时：

```text
host_prepare_ms
h2d_ms
graph_launch_or_kernel_launch_ms
gpu_stream_ms
d2h_ms
e2e_ms
```

## 3.4 测试矩阵

```text
N = 100, 500, 1000
K = 16
repeat = 100
warmup = 20
```

为什么 repeat 增加到 100：

```text
CUDA Graph 主要影响 launch overhead，需要更稳定的 latency 统计。
```

# 4. Phase B：OPT4C Mixed Precision 扫描

## 4.1 目标

在不牺牲 Strict SR 和 pos_p95 的前提下，尝试降低 FP64 计算开销，重点冲刺 N=500。

## 4.2 版本定义

新增 runner 参数：

```bash
--precision-mode fp64
--precision-mode mixed_safe
--precision-mode mixed_mid
--precision-mode mixed_aggressive
--precision-mode fp32_risky
```

### P0：fp64

当前主版本，对照。

### P1：mixed_safe

```text
q: double
target pose: double
FK sin/cos: double or float2double tested
Jacobian: float compute, double accumulate
pose error: double
H = J^T J: double accumulate
linear solve: double
loss/lambda: double
```

目标：质量几乎不变，小幅提速。

### P2：mixed_mid

```text
q: double
FK: float internal, final pose double
Jacobian: float
H/g: mixed accumulate
linear solve: double
loss/lambda: double
```

目标：中等提速，质量仍可接受。

### P3：mixed_aggressive

```text
q: float internal
FK: float
Jacobian: float
H/g: float or mixed
linear solve: double fallback optional
loss/lambda: double
```

目标：尝试大幅提速，但可能质量下降。

### P4：fp32_risky

```text
全链路尽量 FP32
```

只作为 negative/risk experiment，不可直接进入主文，除非质量完全过关。

## 4.3 fallback 机制

对于 P2/P3/P4，必须实现可选 fallback：

```bash
--fallback-mode none
--fallback-mode strict_fail_to_fp64
```

规则：

```text
先用 mixed 解；
如果 Strict 不成功或 pose_cost 超阈值；
则对该 target 使用 fp64 OPT4C 重新求解。
```

输出平均 fallback rate。

注意：

```text
fallback 会增加时间，但可能保住质量。
```

## 4.4 测试矩阵

第一轮快速筛选：

```text
N = 100, 500
repeat = 30
warmup = 10
precision = fp64, mixed_safe, mixed_mid, mixed_aggressive, fp32_risky
fallback = none
```

第二轮完整测试只保留第一轮通过质量的版本：

```text
N = 100, 500, 1000, 5000
repeat = 30
warmup = 10
fallback = none / strict_fail_to_fp64
```

## 4.6 质量门控

任何 mixed 版本要进入主文，必须满足：

```text
N=1000 Strict SR >= 0.93
Strict SR drop vs FP64 <= 1 pp
pos_p95_all <= 8 mm
pos_p95_all increase vs FP64 <= 2 mm
near_limit <= 4%
no NaN/Inf
monotonic pass
```

## 4.7 性能门控

进入主文的性能要求：

```text
N=500 speedup vs FP64 OPT4C >= 1.20x
或
N=500 raw throughput >= cuRobo raw throughput * 1.03
或
N=500 valid throughput >= cuRobo valid throughput * 1.03
```

进入附录：

```text
quality pass
但 speedup < 1.20x
```

进入 negative ablation：

```text
speedup 明显
但 Strict SR drop > 1 pp
或 pos_p95 超阈值
```

## 4.8 特别要求：N=500 目标搜索

如果第一轮没有任何 mixed 版本让 N=500 超越 cuRobo，则允许增加两个局部变体：

```text
mixed_mid_solve64
mixed_mid_solve32_refine64
```

### mixed_mid_solve64

```text
大部分使用 float；
6x6 solve 保持 double。
```

### mixed_mid_solve32_refine64

```text
先 FP32 solve；
再做一次 FP64 residual correction。
```

验收同上。

# 3. Phase A：CUDA Graph E2E 优化

## 3.1 目标

基于 OPT4C-K16 实现 CUDA Graph capture / replay，重点优化：

```text
N=100
N=500
N=1000
```

核心看：

```text
E2E latency
CPU overhead
GPU stream time
repeat stability
N=500 throughput
```

## 3.2 实现要求

新增 runner 参数：

```bash
--graph-mode off
--graph-mode capture_replay
--graph-mode persistent_replay
```

如果已有 graph 支持，则复用；否则新增最小实现。

### graph-mode off

普通 launch，作为对照。

### graph-mode capture_replay

流程：

```text
1. warmup 普通执行；
2. capture 固定 N/K 的完整工作流；
3. instantiate graph；
4. repeat 中只做 graphLaunch；
5. 输出平均值、p50、p95、min、max。
```

### graph-mode persistent_replay

如果数据指针和 buffer 可复用：

```text
1. 初始化时创建固定 N 的 graph；
2. 每轮只更新 input buffer；
3. graphLaunch；
4. 不重复 capture。
```

若实现困难，可只完成 capture_replay。

## 3.3 必须覆盖的 kernel/workflow

至少包含：

```text
OPT4C IK kernel
必要的 memcpy / memset
结果 selection 如果已 fused，则不需要额外 selection kernel
必要的 result copy
```

要分别计时：

```text
host_prepare_ms
h2d_ms
graph_launch_or_kernel_launch_ms
gpu_stream_ms
d2h_ms
e2e_ms
```

## 3.4 测试矩阵

```text

repeat = 100
warmup = 20
```

为什么 repeat 增加到 100：

```text

# 4. Phase B：OPT4C Mixed Precision 扫描

## 4.1 目标

在不牺牲 Strict SR 和 pos_p95 的前提下，尝试降低 FP64 计算开销，重点冲刺 N=500。

## 4.2 版本定义

新增 runner 参数：

```bash
--precision-mode fp64
--precision-mode mixed_safe
--precision-mode mixed_mid
--precision-mode mixed_aggressive
--precision-mode fp32_risky
```

### P0：fp64

当前主版本，对照。

### P1：mixed_safe

```text
q: double
target pose: double
FK sin/cos: double or float2double tested
Jacobian: float compute, double accumulate
pose error: double
H = J^T J: double accumulate
linear solve: double
loss/lambda: double
```

目标：质量几乎不变，小幅提速。

### P2：mixed_mid

```text
q: double
FK: float internal, final pose double
Jacobian: float
H/g: mixed accumulate
linear solve: double
loss/lambda: double
```

目标：中等提速，质量仍可接受。

### P3：mixed_aggressive

```text
q: float internal
FK: float
Jacobian: float
H/g: float or mixed
linear solve: double fallback optional
loss/lambda: double
```

目标：尝试大幅提速，但可能质量下降。

### P4：fp32_risky

```text
全链路尽量 FP32
```

只作为 negative/risk experiment，不可直接进入主文，除非质量完全过关。

## 4.3 fallback 机制

对于 P2/P3/P4，必须实现可选 fallback：

```bash
--fallback-mode none
--fallback-mode strict_fail_to_fp64
```

规则：

```text
先用 mixed 解；
如果 Strict 不成功或 pose_cost 超阈值；
则对该 target 使用 fp64 OPT4C 重新求解。
```

输出平均 fallback rate。

注意：

```text
fallback 会增加时间，但可能保住质量。
```

## 4.4 测试矩阵

## 3.2 实现要求

新增 runner 参数：

```bash

```

如果已有 graph 支持，则复用；否则新增最小实现。

### graph-mode off

普通 launch，作为对照。

### graph-mode capture_replay

流程：

```text
1. warmup 普通执行；
2. capture 固定 N/K 的完整工作流；
3. instantiate graph；
4. repeat 中只做 graphLaunch；

如果数据指针和 buffer 可复用：

```text

2. 每轮只更新 input buffer；
3. graphLaunch；
4. 不重复 capture。
```

若实现困难，可只完成 capture_replay。
