# 图1：系统总体架构图 — 绘制描述词

## 一、图的目标与定位

本图展示本发明的完整数据流和处理阶段：从左侧的**离线预处理阶段**（URDF模型解析、CUDA常量参数导出、标准资产生成），经过中央的**GPU在线求解阶段**（常量内存加载、目标/种子上传、ik_batch_solve kernel launch、结果回读），到右侧的**后处理验证阶段**（收敛率统计、误差分析、同类求解器对比）。

图类型：**系统架构框图 / 数据流图**（System Architecture / Data Flow Diagram）

推荐绘图工具：**draw.io**（免费，支持多层级框图）或 **TikZ**（LaTeX，适合学术论文风格）

## 二、图的结构布局

建议采用**三栏水平布局**（左→中→右），数据流向从左到右以加粗箭头表示。

### 2.1 左栏：离线预处理阶段（Offline Preprocessing Phase）

标题："离线预处理（Python）"

包含以下模块（从上到下排列，以圆角矩形表示）：

| 序号 | 模块名称 | 输入 | 输出 | 代码文件 |
|:----:|---------|------|------|---------|
| 1 | URDF模型解析 | `ur10.urdf` / `panda.urdf` | JointInfo列表、RobotModel对象 | `tools/robot_model.py` |
| 2 | 固定关节折叠 | 相邻fixed+revolute关节对 | 吸收fixed joint origin至前驱revolute joint | `robot_model.py:load_robot_model()` |
| 3 | 常量内存头文件导出 | RobotModel对象 | `ur10_model_constants.h`（16位hex-float精度） | `robot_model.py:export_cuda_constants_header()` |
| 4 | 标准资产生成 | seed=42, N∈{100,500,1000,5000} | 目标位姿（pos+quat+matrix）+ 初始种子（zero_seed） | `tools/generate_standard_assets.py` |

**导出常量内容（在模块3旁边以标注框列出）**：
- c_segment_origins[96] — 6个关节原点变换矩阵（每关节16个FP64）
- c_segment_axes[18] — 6个旋转轴向量（每轴3个FP64）
- c_q_index[6] — 关节角索引映射
- c_T_wrist3_to_tcp[16] — 工具坐标系固定变换
- c_joint_limits[12] — 6个关节的下限和上限
- c_weight_schedule[24] — 4级权重调度（每级6个权重）
- c_lambda_params[4] — LM阻尼参数（λ_base, λ_far, λ_floor, λ_scale）

**箭头**：从模块4指向中栏的"目标位姿文件"和"种子文件"存储图标（磁盘形状）。

### 2.2 中栏：GPU在线求解阶段（GPU Online Solving Phase）

标题："GPU在线求解（CUDA Kernel）"

**从左上到右下流动**，包含以下处理步骤：

| 步骤 | 操作 | CUDA对象 | 数据规模 |
|:----:|------|---------|:--------:|
| ① | 常量内存加载 | `__constant__` 内存广播至所有SM | ~312 bytes（FP64常量参数） |
| ② | 目标位姿上传 | `cudaMemcpy` Host→Device | N×16 doubles（T_tgt矩阵） |
| ③ | 种子上传 | `cudaMemcpy` Host→Device | N×6 doubles（q_seed） |
| ④ | **ik_batch_solve kernel launch** | Grid(N,1,1), Block(128,1,1) | N个block并行 |
| ⑤ | Kernel内部DLS迭代循环 | 共享内存 + 寄存器（详见代码） | 最多50次迭代/block |
| ⑥ | 结果回读 | `cudaMemcpy` Device→Host | N×6 q_result + N×2 errors + N iters |

**步骤④—⑤的详细展开（在kernel框内以子图表示）**：

右上角插入Block/Warp/Lane映射的微缩示意图（一个小方块内展示4个Warp分区）：
- W0 (绿色): Lane 0 → FK + Error + LDLᵀ + Damping + Converge
- W1 (蓝色): Lanes 32-37 → Jacobian 6列并行
- W2 (橙色): Lanes 64-99 → H 36路并行 + g 6路并行
- W3 (红色): Lanes 96-101 → 关节更新 + 限位投影

**在kernel框下方标注**：
- 共享内存：~1,616 bytes/block
- 寄存器：94 regs/thread (NCU实测)
- 常量内存：~312 bytes（广播至所有SM的L1缓存）

### 2.3 右栏：后处理验证阶段（Post-Processing Verification Phase）

标题："后处理验证（Python）"

包含以下模块（从上到下排列）：

| 序号 | 模块名称 | 功能 | 输出 |
|:----:|---------|------|------|
| 1 | 收敛率统计 | 统计 position_err<0.03m AND rot_err<0.5236rad 的目标比例 | 收敛率（ConvRate） |
| 2 | 时间度量 | GPU event计时（kernel执行时间）、host API total time（端到端） | GPU time (ms)、host API time (ms) |
| 3 | 吞吐量计算 | Query Throughput = N / T_total（单位：targets/s） | Throughput (t/s) |
| 4 | 同类求解器对比 | 统一口径下与cuRobo/PyRoki/KDL/numeric_dls对比 | 对比表 + 加速比 |
| 5 | NCU Profiling | Nsight Compute分析kernel瓶颈（计算吞吐/DRAM/L1/寄存器/Bank冲突） | NCU报告 |

**底部汇总框**：展示关键结果指标（以数据卡片形式）：

| 指标 | 值 |
|------|-----|
| B5 Throughput @ N=5000 | 180,962 t/s |
| B5 vs cuRobo @ N=100 | 37.6× |
| B5 vs cuRobo @ N=5000 | 1.25× |
| B5 收敛率 | 99.98%+ |
| 计算吞吐利用率 | 60.73% |
| DRAM吞吐利用率 | 1.16% |

## 三、图中连线与数据流

- **离线→GPU**：以"常量内存头文件"、"目标位姿文件"、"种子文件"三条虚线连接至中栏顶部
- **GPU内部**：实线箭头连接步骤①→②→③→④→⑤→⑥，④和⑤在kernel框内部
- **GPU→验证**：以"results数组"、"errors数组"、"iterations数组"三条实线箭头连接至右栏顶部
- **验证内部**：实线箭头连接1→2→3→4, 4→5为虚线（profiling为独立步骤）

## 五、尺寸建议

- 画布：横向A3或16:9宽屏比例（约1600×900像素等效）
- 三栏宽度比：左:中:右 ≈ 1 : 1.3 : 1
- 栏间距：约40像素
- 模块间垂直间距：约30像素
- 字体大小：模块标题14pt，正文11pt，标注9pt

## 六、特别注意事项

1. **kernel框必须比周围模块更大、更突出**——这是整个发明的核心
2. kernel框内的4-Warp微缩示意图很重要，需要清晰标注W0/W1/W2/W3的分工
3. 离线阶段的"固定关节折叠"步骤是论文强调的一致性修复点，应保留但不需要过度突出
4. 右栏底部的结果卡片数据需要与最新论文数据一致（B5 N=5000: 180,962 t/s等）
5. 所有模块应使用圆角矩形，数据存储使用圆柱体图标或磁盘图标
6. 箭头应标注数据类型（如"FP64常量"、"N×16 目标矩阵"、"N×6 结果"）
