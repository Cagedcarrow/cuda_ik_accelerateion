# 7. 讨论

## 7.1 为什么标准化后旧 CUDA kernel 会失效

这项工作的一个重要经验是：把"自定义装配体上调通"的 CUDA IK kernel 直接迁移到官方 UR10，失败并不意味着 GPU 思路本身错误，很多时候是**定义不一致**先于**性能不足**。

在本文中，最典型的症状是：

- 位置误差几乎压到零；
- 姿态误差却长期停留在错误分支；
- 收敛率在旧迁移版上大幅下降。

如果不先修这些定义问题，而是直接继续做 block size、shared memory 或 launch 优化，得到的"更快结果"并不可信。

## 7.2 公平 benchmark 比"漂亮数字"更重要

本文专门把以下条件固定下来：

- 同一官方 UR10 模型；
- 同一 `tool0`；
- 同一 target/seeds 资产；
- 同一阈值；
- 清晰区分主对比 solver 与参考 solver；
- 单 solver 失败时保留错误日志，而不是静默跳过。

这种"把限制写清楚"的做法，比简单给出一个看上去更整齐的排行榜更有研究价值。

## 7.3 消融研究的核心发现

通过 B0-B6 逐级消融，本文得到了四个关键发现：

### 1. 内存层次优化在 IK 场景中的作用有限

常量内存（B1）和 PaddedMat6x8（B2）在小批量（N=100）上提供合计约 5% 的吞吐提升，在大批量（N≥500）上收益可忽略。这是因为 UR10 的 FK 工作集（96 个 doubles origins + 18 doubles axes）即使放在全局内存中也能被 L1 缓存高效容纳。这与许多以大规模矩阵为核心的 GPU 应用不同——在那些场景中常量内存和共享内存通常贡献更大的收益。

### 2. 自适应阻尼的决定性影响

自适应阻尼对收敛率的决定性影响是一个重要发现。当使用固定 λ（B0-B2）时，N=5000 的收敛率仅有 83.4%，平均需要 30.9 次迭代。而启用自适应阻尼后（B3），收敛率回升到 100%，平均迭代次数降至 13.1，吞吐提升 147%。

有趣的是，自适应阻尼**在小批量上反而有害**——在 N=100 时吞吐下降 63%。这是因为小批量时 GPU 有充足的空闲线程，固定 λ 即可在 4.3 次迭代内收敛，自适应阻尼的分支逻辑（if-else、sqrt、fmin/fmax）变成了额外开销。这提醒我们：优化策略的效果高度依赖于批处理规模。

### 3. 混合精度的最大化加速

从 B4（FP64 全精度）到 B5（FP32 主体 + FP64 LDLT 关键路径），混合精度带来了 **148–154% 的吞吐提升**，是所有消融级别中幅度最大的单一变更。这一提升主要来自 FK、Jacobian 和 Hessian 构造中 FP64 运算量的减少，以及 FP32 数据宽度减半带来的共享内存访问压力缓解。与此同时，LDLT 求解器、阻尼调节和收敛判定这些关键路径保持 FP64，使得收敛率仍然维持在 99.98% 以上。

NCU 分析进一步证实了这一设计的有效性：B5 的 kernel 执行时间从 B4 的 2,920 μs 降至 827 μs（缩短 72%），共享内存 bank 冲突从 3,522 次降至 1,295 次（减少 49%，因 FP32 数据宽度减半）。更重要的是，**FP64 pipeline 仍然保持着 60.7% 的利用率**——说明 LDLT 求解器仍然为 SM 提供了充足的计算负载，从当前 NCU 指标看，混合精度引入的类型转换没有表现为主导瓶颈；主要瓶颈仍为计算吞吐与寄存器压力。

### 4. 步长钳位与分支对齐的收益为负

B4 中引入的步长钳位（0.35 rad）和分支对齐（关节角 π-wrap 校正）在所有批量上持续降低吞吐 15–20%，而收敛率已为 100% 不变。这表明 0.35 rad 的步长限制对 UR10 的关节空间过于保守，建议面向吞吐的推理采用 B5 配置（混合精度 + 自适应阻尼，关闭步长钳位与分支对齐）。

## 7.4 与 cuRobo 的技术路线差异

本文与 cuRobo 代表了 GPU IK 求解的两种不同优化哲学：

**本文路线（GPU 硬件适配）**：
- 1 block/target 的轻量级映射；
- 混合精度（FP32 主体 + FP64 LDLT）；
- 寄存器级 6×6 LDLT 求解器；
- 常量内存广播机器人参数；
- 单 kernel 完成全部 DLS 迭代。

**cuRobo 路线（算法框架优化）**：
- L-BFGS 优化器 + particle 搜索；
- FP32 精度以获得更高计算吞吐；
- 多粒子并行增加 GPU 利用率；
- 基于 PyTorch 的通用框架。

本文的 B3（FP64）版本在 N=100 时领先 cuRobo 18.3 倍，但在 N=5000 时落后 2.0 倍。引入混合精度后（B5），本文方法在 N=5000 上以 180,962 targets/s 达到 cuRobo 吞吐（144,855 targets/s）的 1.25 倍。该结果提示，在本文测试口径下，精度配置和底层实现对大批量吞吐具有显著影响；cuRobo 在 FP64-only 对照下表现出的优势，不能简单归因于算法框架本身，也受到 FP32 计算路径和多 particle 并行组织方式的共同影响。

在本文测试范围内，两条路线不再存在明确的交叉点：混合精度的引入使 B5 配置在 N=100-5000 的测试批量上均达到或超过 cuRobo 的 IK 吞吐水平。

## 7.5 架构级分析：Nsight Compute 的定量证据

本文的所有优化决策都有 NCU profiling 数据的支撑：

### 计算边界分析

N=100 的 full NCU profiling 显示：

- **Compute throughput 60.73–66.89%**，DRAM throughput 仅 1.16–1.56%——kernel 明确为计算边界而非内存边界；
- **FP64 pipeline 利用率最高**（60.7%），即使在混合精度版本中，LDLT 求解器的 FP64 计算仍然占据主导；
- **寄存器压力是 occupancy 的主限因素**——94–98 个寄存器/线程将理论 occupancy 限制在约 33%。

### 混合精度的硬件证据

B5 的 NCU 数据为混合精度的有效性提供了直接证据：

- Kernel 时长从 2,920 μs 降至 827 μs（**−72%**）；
- SM throughput 从 66.89% 降至 60.73%（偏高的计算压力被缓解）；
- Bank conflicts 从 3,522 降至 1,295（**−49%**），但占总波前的比例仍不足 1%。

### CUDA Graph 的零开销验证

B6（B5 + CUDA Graph）的 event-based 计时显示，`cudaGraphLaunch` 的 kernel 执行时间与直接 `<<<>>>` launch 在测量噪声范围内一致（0.9008 ms vs 0.8991 ms，差异 < 0.2%）。这表明在当前 kernel 配置下，launch overhead 不是性能瓶颈——CUDA Graph 的优化潜力在更轻量级的 kernel 中才能体现。

### Bank Conflict 的非瓶颈确认

NCU 的精确计数显示，B5 的 1,295 次存储 bank 冲突仅占总共享访问波前的约 1%。即使完全消除这些冲突，预期加速也低于 1%。这一结论避免了在不重要的优化方向上投入精力。

## 7.6 为什么本文不把随机 target 测试写成路径规划

一些 GPU 机器人论文会把 IK benchmark、collision-free IK、trajectory optimization 和 motion planning 放在同一个叙事里。本文刻意避免这种写法，因为当前完成的实验本质上是：

- 给定一批可达末端位姿；
- 求对应的关节解；
- 比较批量求解吞吐与收敛率。

即使 target profile 是沿 home pose 附近生成的平滑查询，它仍然不是时间连续轨迹的优化问题，也不是全局路径规划问题。把它误写成 motion planning，会夸大当前工作的范围。

## 7.7 对后续工作的启示

1. **Panda 7DOF 完整 benchmark**：将当前独立验证的 7DOF CUDA kernel 集成到主 benchmark 框架中，与 cuRobo 等求解器进行统一口径对比。主要挑战在于 7×7 LDLT 的寄存器压力控制和冗余自由度下的多 seed 策略设计。

2. **多 seed 策略**：评估在每个目标上发射 2–4 个不同初始 seed 对收敛率和吞吐的联合影响，作为 cuRobo particle 搜索的轻量级替代。

3. **编译器优化**：利用 `__launch_bounds__` 和寄存器分配提示进一步降低寄存器压力，提高 occupancy。

4. **大规模 batch 的 grid 调度优化**：在 N=5000+ 场景中，分析 grid 尾块（partial wave）效应，探索 grid 调度策略以消除 SM 负载不均衡。

5. **FP64 计算路径的进一步优化**：LDLT 求解器当前使用纯 FP64 计算，可探索迭代精化（iterative refinement）等混合精度线性求解技术，在保持精度的同时减少 FP64 计算量。
