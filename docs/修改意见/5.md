## 总体评价

这版**明显比上一版干净**。主线已经基本收束为：

> 标准 UR10 批量 IK → DLS 小矩阵建模 → CUDA block/warp/register 映射 → B0-B6 消融 → cuRobo 性能边界 → NCU 证据链 → Panda 7DOF 正确性验证。

这条线现在是清楚的。摘要、引言、贡献、实验章节已经大幅删除了铲斗、273 锚点、52,416 IK、碰撞检测、轨迹回放等支线内容，论文不再像上一版那样同时写两篇文章。

但还没有完全清干净。当前仍有**4 类硬问题**需要修：

1. **旧工程支线残留；**
2. **第 4 章仍混入旧消融数据；**
3. **时间口径和吞吐定义仍不一致；**
4. **硬件推导仍有过强断言。**

下面逐项审阅。

# 1. 最大进步

> 本文研究的是标准机械臂批量逆运动学的 GPU 实现，而不是路径规划、轨迹回放或碰撞感知 IK。

这比上一版的五六个贡献稳很多。现在贡献闭环是清楚的。

# 5. 时间口径与吞吐定义仍不一致

## 5.1 第 5 章说跨求解器用 host_api_total_time

你写：

> 跨求解器对比时，以 host_api_total_time 作为统一口径。

但第 6 章主表列名是：

> GPU时间 (ms)

并且吞吐是按这个时间算出来的。例如：

[
5000 / 27.630\text{ ms} \approx 180{,}962 \text{ targets/s}
]

这明显是 GPU 时间，不是 host API total time。

## 处理方式

你必须二选一。

### 方案 A：主表就是 GPU 口径

那第 5 章要改成：

> 主 GPU 对比采用 GPU event 计时口径；CPU 参考求解器采用 host API 口径，因此不与 GPU 主表进行严格等口径排名。

### 方案 B：主表全部改成 host_api_total_time

那需要重新填主表，不能用现在的 GPU 时间。

我建议用方案 A，因为你现在的核心结论基于 GPU 时间。那就不要声称“跨求解器统一使用 host_api_total_time”。

建议改成：

> CUDA 与 cuRobo 的主 GPU 对比采用可复现的 GPU 侧计时口径；CPU 参考求解器仅作为数量级参照，不参与 GPU 主结论。host_api_total_time 作为工程端到端补充口径保留。

# 6. 吞吐量定义和表格计算不一致

第 3 章你定义：

[
\text{Throughput}=\frac{N_{\text{converged}}}{T_{\text{total}}}
]

但第 6 章表格明显用的是：

[
\frac{N}{T}
]

例如 N=500，B5：

* ConvRate = 0.998；
* GPU时间 = 3.338 ms；
* 如果按 (N_{\text{converged}})，吞吐应接近 (499/0.003338)；
* 表格里是 (500/0.003338)。

差异不大，但定义必须严谨。

## 建议

定义两个指标：

[
\text{Query Throughput}=\frac{N}{T_{\text{total}}}
]

[
\text{Successful Throughput}=\frac{N_{\text{converged}}}{T_{\text{total}}}
]

你的主表当前使用的是 **Query Throughput**。那就把定义改成：

> 本文主表报告 Query Throughput，即单位时间处理的目标总数；收敛率单独报告。对于收敛率不为 1 的配置，Successful Throughput 可由 Query Throughput × ConvRate 得到。

这样最稳。

# 8. 硬件推导仍有过强断言

## 8.1 “Ada 每 SM 16,384 个寄存器”建议删除

你还在写：

> Ada Lovelace 每 SM 16,384 个 32 位寄存器。

这个数值如果没有官方引用，非常危险。你后面还用它推 occupancy。建议全部删除，改成 NCU 实测表述。

改法：

> 具体寄存器分配与 occupancy 以 Nsight Compute 报告为准。实测结果显示，该 kernel 使用 94–98 registers/thread，achieved occupancy 约 32%–33%，且无 local memory spilling。

---

## 8.2 “cuBLAS 5–10 μs、50–200 倍”要降级

你写：

> cuBLAS 求解同一 6×6 系统延迟约 5–10 μs，register LDLT 加速 50–200 倍。

如果你没有专门测过 cuBLAS 6×6 batched solver，这个说法太硬。

建议改成：

> 对 (6\times6) 极小矩阵而言，通用线性代数库的 kernel launch 与调度开销可能超过实际分解计算量。因此，本文采用寄存器级专用实现以避免额外库调用和全局内存往返。

如果你确实测过，再补“本文实测”。

---

## 8.3 “零全局内存访问，零共享内存访问”要限定

LDLT 求解本身可以寄存器内完成，但整个 kernel 当然有全局内存读写和共享内存访问。你要写清楚：

> LDLT 求解阶段本身不访问全局内存和共享内存。

不要写得像整个 kernel 零访存。
