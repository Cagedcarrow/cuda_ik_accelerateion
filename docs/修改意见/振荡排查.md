# cuRobo 批量规模振荡 / latency spike 排查任务说明

## 一、任务背景

当前论文 benchmark 中观察到 cuRobo 在部分 batch size 下出现非单调耗时跳变现象：

* 正常模式：host 调用时间约 31–33 ms；
* 退化模式：host 调用时间约 218–239 ms；
* 退化点可能包括：N=4000、7000、9000、10000；
* 正常点可能包括：N=2000、3000、5000、6000、8000；
* CUDA B5 在相同 N 范围内表现为接近线性的 kernel 时间增长。

当前论文只能将该现象表述为：

> 本实验配置下观察到的 cuRobo host-call elapsed time 的 batch-size-sensitive latency spikes。

不能直接断言：

> cuRobo 算法本身存在固有振荡；
> 退化根因一定是 PyTorch CUDA Caching Allocator；
> 退化根因一定是 workspace 重分配。

本次排查目标是收集证据，判断该现象到底来自：

1. benchmark 脚本计时口径问题；
2. cuRobo solver 初始化 / CUDA graph capture / replay 问题；
3. batch size / max_batch_size / tensor shape 改变导致的 workspace 重建；
4. PyTorch CUDA allocator 分配、释放或缓存状态变化；
5. CUDA stream synchronization；
6. GPU warmup、运行顺序、后台进程或显存碎片污染；
7. 其他 cuRobo 内部实现机制。

# 三、第一阶段：复现原始振荡现象

## 3.1 目标

确认原始 benchmark 中观察到的 cuRobo 耗时跳变是否可稳定复现。

## 3.2 测试 N 列表

使用以下 batch size：

```python
N_LIST = [100, 500, 1000, 2000, 3000, 4000, 5000, 6000, 7000, 8000, 9000, 10000]
```

## 3.3 固定条件

请固定以下条件：

```text
robot: UR10
tool: tool0
target asset: 与论文 benchmark 完全一致
seed strategy: zero_seed
threshold: Medium = 10 mm / 5°
repeat: 30
warmup: 3
device: 当前 CUDA GPU
```

## 3.4 计时口径

必须分别记录以下时间：

```text
host_wall_time_ms:
    Python 端 time.perf_counter() 包围 cuRobo solve_pose() 或等价求解调用。

cuda_event_time_ms:
    如果能够在 cuRobo 调用内部或外部插入 CUDA event，则记录 CUDA event 时间。
    如果无法准确记录内部 kernel 时间，则填 NaN，并在报告中说明原因。

torch_synchronize_time_ms:
    若每次 solve 后调用 torch.cuda.synchronize()，记录同步前后差值。
```

注意：

* `host_wall_time_ms` 是主要观察对象；
* 不要把它叫做 cuRobo kernel time；
* 不要把它直接称为 GPU kernel 时间。

# 四、第二阶段：顺序运行 vs 随机顺序运行

## 4.1 目标

排查退化是否由测试顺序污染、显存缓存历史状态或前一个 N 的状态影响导致。

## 4.2 顺序扫描

按如下顺序运行：

```python
ORDERED_N_LIST = [100, 500, 1000, 2000, 3000, 4000, 5000, 6000, 7000, 8000, 9000, 10000]
```

输出：

```text
curobo_latency_scan_ordered.csv
```

## 4.3 随机顺序扫描

至少运行 3 组不同随机顺序，例如：

```python
RANDOM_ORDER_1 = [8000, 4000, 1000, 7000, 5000, 9000, 3000, 10000, 2000, 6000, 500, 100]
RANDOM_ORDER_2 = [4000, 5000, 7000, 8000, 9000, 10000, 3000, 2000, 1000, 500, 100, 6000]
RANDOM_ORDER_3 = [10000, 9000, 8000, 7000, 6000, 5000, 4000, 3000, 2000, 1000, 500, 100]
```

输出：

```text
curobo_latency_scan_randomized.csv
```

## 4.4 判断标准

如果 N=4000、7000、9000、10000 在随机顺序中仍稳定退化，说明退化与 N 本身更相关。

如果退化点随运行顺序移动，说明可能是 allocator 历史状态、显存碎片或 warmup 状态污染。

# 五、第三阶段：每个 N 单独新进程运行

## 5.1 目标

排查同一 Python 进程内 PyTorch allocator 缓存状态、cuRobo solver 残留状态是否影响结果。

## 5.2 实现方式

写一个主控脚本：

```bash
run_fresh_process_scan.py
```

该脚本对每个 N 启动一个独立 Python 子进程，例如：

```bash
python bench_single_curobo_n.py --N 4000 --repeat 30 --warmup 3 --output results/fresh_N4000.json
python bench_single_curobo_n.py --N 5000 --repeat 30 --warmup 3 --output results/fresh_N5000.json
```

每个子进程完成后退出，确保：

* Python 进程重启；
* PyTorch allocator 状态重置；
* cuRobo solver 重新初始化；
* CUDA context 重新创建。

输出汇总：

```text
curobo_latency_scan_fresh_process.csv
```

## 5.3 判断标准

如果 fresh process 后退化点消失，说明原始退化可能来自同一进程内 allocator / cache / solver 状态。

如果 fresh process 后退化点仍存在，说明退化可能与该 N 下的 cuRobo 配置、tensor shape、workspace 或 CUDA graph 路径相关。

---

# 六、第四阶段：固定 max_batch_size 排查

## 6.1 目标

排查退化是否由每个 N 都重新设置 `max_batch_size=N` 导致。

## 6.2 实验设计

固定：

```python
max_batch_size = 10000
```

然后分别测试实际 N：

```python
actual_N = [100, 500, 1000, 2000, 3000, 4000, 5000, 6000, 7000, 8000, 9000, 10000]
```

实现方式：

* cuRobo solver 初始化时始终使用 `max_batch_size=10000`；
* 实际输入只取前 N 个 target；
* 如果 cuRobo 需要 padding，则显式记录是否发生 padding；
* 保持 target、seed、threshold 与论文 benchmark 一致。

输出：

```text
curobo_latency_fixed_max_batch.csv
```

## 6.3 判断标准

如果固定 `max_batch_size=10000` 后原来的 N=4000、7000、9000 退化消失，则说明退化很可能与：

```text
solver 初始化时的 max_batch_size；
CUDA graph capture shape；
workspace size；
tensor shape；
内部 padding / allocation 路径；
```

有关。

如果固定 `max_batch_size=10000` 后退化仍存在，则说明 actual_N 对 solve path 仍有影响，需要进一步看 profiler。

---

# 七、第五阶段：记录 PyTorch CUDA 显存状态

## 7.1 目标

判断退化点是否对应显存 allocated / reserved / max_reserved 的异常变化。

## 7.2 每次 solve 前后记录

在每个 repeat 中，至少记录：

```python
torch.cuda.memory_allocated()
torch.cuda.memory_reserved()
torch.cuda.max_memory_allocated()
torch.cuda.max_memory_reserved()
```

并在每个 N 的 warmup 前、warmup 后、repeat 后分别导出：

```python
torch.cuda.memory_summary()
```

输出目录：

```text
results/curobo_memory_summary_logs/
```

建议文件名：

```text
memory_summary_N4000_before.txt
memory_summary_N4000_after_warmup.txt
memory_summary_N4000_after_repeat.txt
```

## 7.3 额外建议

如果可行，在每个 N 测试前分别测试两种模式：

### 模式 A：不清 cache

```python
# do nothing
```

### 模式 B：清 cache

```python
torch.cuda.empty_cache()
torch.cuda.reset_peak_memory_stats()
torch.cuda.synchronize()
```

输出字段中加入：

```text
cache_policy: keep_cache / empty_cache_before_N
```

## 7.4 判断标准

如果退化点伴随 `memory_reserved` 或 `max_memory_reserved` 突然增加，说明 allocator / workspace 假设增强。

如果退化点没有显存统计变化，则可能是 stream synchronization、CUDA graph 或 solver 内部路径导致。

# 十一、最终报告要求

生成：

```text
curobo_diagnosis_report.md
```

报告必须包含以下章节：

## 1. 复现结论

回答：

```text
原始振荡现象是否复现？
退化点是否仍为 N=4000 / 7000 / 9000 / 10000？
正常点和退化点的 host time 分别是多少？
```

## 2. 顺序敏感性

回答：

```text
随机顺序运行后退化点是否改变？
如果改变，说明什么？
如果不改变，说明什么？
```

## 3. 进程隔离结果

回答：

```text
fresh process 是否消除退化？
如果消除，可能是进程内 allocator/cache 状态；
如果未消除，可能是 N 对应的 shape/workspace/graph 路径。
```

## 4. fixed max_batch_size 结果

回答：

```text
固定 max_batch_size=10000 后，退化是否消失？
若消失，说明 max_batch_size / graph shape / workspace size 是关键因素。
若未消失，说明 actual_N 或内部处理路径仍影响性能。
```

## 5. 显存统计结果

回答：

```text
退化点是否对应 memory_reserved / memory_allocated / max_reserved 异常跳变？
是否出现 allocator 行为异常？
```

## 6. Profiler 结果

回答：

```text
退化点是否出现 cudaMalloc / cudaFree / cudaDeviceSynchronize / cudaGraphInstantiate / graph recapture？
kernel 数量是否变化？
单 kernel 时间是否变化？
host idle / wait 时间是否变化？
```

## 7. 最可能原因排序

按证据强弱排序：

```text
1. 最可能原因
2. 次可能原因
3. 可排除原因
4. 仍无法确认的原因
```

注意：如果没有直接 profiler 证据，不能写“确定根因”。

## 8. 论文建议写法

根据排查结果，给出论文中推荐表述。

如果只有现象复现、没有 profiler 证据，推荐写：

```text
本文在当前 cuRobo benchmark 配置下观察到 batch-size-sensitive host-call latency spikes。该现象表现为部分 N 值下 solve_pose 调用时间从约 32 ms 跳变至约 230 ms，且与收敛率或阈值变化无明显对应关系。结合 cuRobo 对 CUDA graph / tensor shape 稳定性的依赖以及 PyTorch CUDA allocator 的缓存机制，本文推测该现象可能来自 workspace 管理、allocator 行为、stream synchronization 或 tensor 生命周期管理中的某一环节；但由于尚未通过 Nsight Systems / CUDA API trace 完成唯一归因，本文不将其表述为 cuRobo 算法本身的固有缺陷。
```

如果 profiler 确认存在 cudaMalloc/cudaFree 或 graph recapture，则推荐写：

```text
Nsight Systems / Torch profiler 显示，退化点伴随 [具体事件]，因此该 latency spike 更可能来自 [具体机制]，而非 IK 迭代计算本身。
```

# 十二、禁止事项

请不要做以下事情：

* 不要修改论文主数据，除非排查结果证明原始数据错误；
* 不要把 host wall time 写成 cuRobo kernel time；
* 不要在没有 profiler 证据时断言 allocator 是根因；
* 不要只跑一次就下结论；
* 不要只报告平均值，必须报告 std / min / max / median；
* 不要删除不符合预期的结果；
* 不要把 CUDA B5 kernel-only 时间与 cuRobo host-call 时间混称为同一 GPU 时间；
* 不要把 cuRobo 的 latency spike 写成 cuRobo 算法缺陷；
* 不要把 single process 结果和 fresh process 结果混在一张表里而不标注。

